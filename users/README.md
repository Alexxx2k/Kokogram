# Сервис пользователей

Сервис реализует регистрацию, вход и сессии, профиль, поиск и аватары.
Контакты и блокировки в этот тикет не входят.

## Локальный запуск

Нужны Python 3.12, Docker Compose и `make`. Из корня репозитория:

```bash
# Только при первом запуске, если .env ещё нет:
cp .env.example .env
```

Заполните `URL_SIGNING_SECRET` в `.env` случайным значением, например результатом
`openssl rand -hex 32`. Существующий `.env` не перезаписывайте.
Команды ниже рассчитаны на Bash и shell-совместимый формат `.env`:

```bash
make up

cd users
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cd ..
pip install -r db/requirements.txt

# Локальный uvicorn и прямой запуск Alembic сами .env не загружают.
set -a
source .env
set +a
export POSTGRES_HOST=localhost
export S3_ENDPOINT_URL=http://localhost:8333

make migrate
```

При нестандартном порте PostgreSQL задайте также `POSTGRES_PORT`. Если задан
`DATABASE_URL`, он имеет приоритет над `POSTGRES_*`. Команды активации выше —
для Linux/macOS; в Git Bash на Windows используйте `source .venv/Scripts/activate`.

Перейдите в каталог сервиса:

```bash
cd users
```

Для аватаров создайте bucket по инструкции [ниже](#аватары-и-s3) в активном
окружении. Для регистрации и профиля наличие bucket не требуется.
Затем из этого же каталога запустите приложение:

```bash
uvicorn app.main:app --reload
```

API сервиса: `http://127.0.0.1:8000`; Swagger: `/docs`; OpenAPI: `/openapi.json`.
Для прямых запросов префикс `/api/v1` не нужен.

## Запуск users в Docker

Подготовьте `.env`, инфраструктуру, миграции и bucket так же, как для локального
запуска. Из корня репозитория:

```bash
docker compose -f docker-compose.test.yml --profile full build users
docker compose -f docker-compose.test.yml --profile full run --rm --no-deps -p 127.0.0.1:8001:8000 users
```

В этом варианте сервис доступен напрямую на `http://127.0.0.1:8001`.
`run` использует настройки users из Compose: PostgreSQL — `postgres:5432`,
S3 — `seaweedfs:8333`. Окружение процесса приложения берётся из секции
`services.users.environment`, а не автоматически из всех переменных `.env`.
Произвольные изменения локальных лимитов не попадают в контейнер без добавления
соответствующих переменных в эту секцию.

`make up-full` запускает все компоненты. При обычном `up` порт users наружу не
публикуется; доступ через `/api/v1` требует работающей реализации Gateway.
Показанный выше `run` позволяет проверить users отдельно от готовности Gateway.

## Настройки

Настройки читаются из переменных окружения. Файл `.env` автоматически не загружается:
при локальном запуске переменные нужно экспортировать в окружение процесса.

| Переменная | Значение по умолчанию / назначение |
|---|---|
| `DATABASE_URL` | URL PostgreSQL; если не задан, собирается из `POSTGRES_*` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | `kokogram` |
| `POSTGRES_HOST`, `POSTGRES_PORT` | `localhost`, `5432` |
| `S3_ENDPOINT_URL` | `http://localhost:8333` |
| `S3_REGION` | `us-east-1` |
| `S3_BUCKET` | `kokogram` |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Пустые; учётные данные выбранного S3-хранилища |
| `URL_SIGNING_SECRET` | Без значения по умолчанию; обязателен при запуске сервиса |
| `SIGNED_URL_TTL_SECONDS` | `900`, допустимо от 1 до 900 секунд |
| `SESSION_TTL_DAYS` | `30`, допустимо от 1 до 30 суток |
| `AVATAR_MAX_BYTES` | `5242880`, допустимо от 1 до 5242880 байт |

`URL_SIGNING_SECRET` должен совпадать у сервисов пользователей, чатов и сообщений.
В Docker адреса зависимостей задаются именами контейнеров, например
`POSTGRES_HOST=postgres` и `S3_ENDPOINT_URL=http://seaweedfs:8333`.

Настройки и общие зависимости предоставляются функциями в `app/api/dependencies.py`.
В HTTP-проверках их можно подменять через `app.dependency_overrides`.
Обработчики ошибок и JSON-логирование подключены в `app/main.py`; middleware
сохраняет входящий `X-Request-ID` или создаёт новый и возвращает его в ответе.

На этом этапе `/health` возвращает `{"status": "ok"}` и подтверждает работу приложения;
проверки доступности PostgreSQL и S3 ещё не подключены.

## Слой данных

`app/models.py` содержит обычные Python-объекты `User` и `Session`. Интерфейсы
репозиториев находятся в `app/ports/`, реализации SQLAlchemy — в `app/adapters/`.
Адаптеры используют асинхронный psycopg 3; версии SQLAlchemy и psycopg совпадают
с зависимостями миграций.

Пул подключений создаётся при запуске приложения и освобождается при остановке.
DI-функции `get_user_repository` и `get_session_repository` используют общую
сессию БД в рамках запроса. Транзакция завершается до отправки ответа: при успехе
выполняется commit, при исключении — rollback. Репозитории сами не делают commit.

Описания таблиц соответствуют миграции `0001_users`; автоматически таблицы не
создаются. Перед обращением к БД необходимо применить миграции из корня проекта.
ID и временные поля обязательны при создании объектов: их передаёт бизнес-логика
через `IdGenerator` и `Clock`. У репозиториев нет генераторов ID и времени.

Конфликты ограничений `uq_users_email`, `uq_users_phone` и `uq_users_username`
преобразуются в `email_taken`, `phone_taken` и `username_taken` соответственно.
Ошибки подключения и таймауты преобразуются в `service_unavailable`.
Другие нарушения целостности не маскируются под конфликты пользователя.

Репозиторий сессий принимает только `token_hash`; вычисление SHA-256 и проверку
`expires_at` выполняет `SessionService`.

## Регистрация

`POST /auth/register` принимает JSON с `username`, `password` и хотя бы одним
из полей `email` и `phone`. Авторизация не требуется. Пример для локального
сервиса (при запуске через Gateway добавляется префикс `/api/v1`):

```bash
curl -i http://localhost:8000/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"hello123","email":"Alice@Example.org"}'
```

Правила:

- Username: от 3 до 12 символов, латинские буквы, цифры и `_`.
- Пароль: от 6 до 12 символов, хотя бы одна буква и одна десятичная цифра.
  Пароль не обрезается и не нормализуется; буквы могут быть нелатинскими.
- Email проверяется библиотекой `email-validator` без DNS-запросов и сохраняется
  в нижнем регистре; пробелы по краям удаляются.
- Телефон: 11 цифр с началом `8` или `7`, либо международная запись с `+7`.
  Пробелы, круглые скобки и дефисы допускаются. Результат — `+7XXXXXXXXXX`.
- Если переданы и email, и телефон, проверяются и сохраняются оба.

При успехе возвращается `201` и объект `{id, username, status, avatar_url}`.
У нового пользователя статус и аватар равны `null`. Email, телефон и хэш пароля
в этот ответ не включаются. Регистрация не создаёт сессию входа.

Нарушения правил возвращают `422 validation_error` с полем и причиной
в `error.details`; конфликты уникальности — `409 email_taken`, `phone_taken`
или `username_taken`. Пароль хэшируется bcrypt с cost 10 в отдельном потоке,
в БД передаётся только хэш. Нагрузочные требования NF_Perf_1–3 пока не измерялись.

## Вход и сессии

`POST /auth/login` принимает JSON `{login, password}`. Логин — email или российский
номер телефона; используются те же правила нормализации, что при регистрации.
При неверном логине или пароле возвращается `401 invalid_credentials`.

```bash
curl -i http://localhost:8000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"Alice@Example.org","password":"hello123"}'
```

Успешный ответ: `200`, `{token, expires_at, user}`. `user` содержит те же поля,
что ответ регистрации. Токен создаётся `TokenGenerator` (в обычном запуске —
32 случайных байта в URL-safe представлении). Исходный токен возвращается клиенту;
в PostgreSQL сохраняется только его SHA-256 хэш. Время создания берётся из `Clock`,
срок действия — `SESSION_TTL_DAYS` (по умолчанию 30 суток). Каждый вход создаёт
отдельную сессию, предыдущие сессии продолжают действовать.

`POST /auth/logout` требует `Authorization: Bearer <token>` и удаляет только текущую
сессию. Успех — `204` без тела; отсутствующий, неизвестный или просроченный токен —
`401 unauthorized`. Остальные сессии пользователя не удаляются.

Внутренний `POST /internal/sessions/verify` принимает JSON `{token}` и возвращает
`200`, `{user_id}`. Токен ищется по хэшу; при `clock.now() >= expires_at` он уже
недействителен. Пустой, неизвестный, просроченный или завершённый токен возвращает
`401 unauthorized`. Этот эндпоинт предназначен для Gateway; наружу пути `/internal`
не маршрутизируются. Проверка срока не продлевает сессию.

Просроченные записи сейчас остаются в таблице, но не принимаются при авторизации;
фоновая очистка не реализована.

DI-функция `get_current_user` проверяет Bearer-токен через `SessionService` и
получает пользователя из репозитория. Она используется защищёнными эндпоинтами
профиля; заголовок `X-User-Id` не используется как самостоятельное доказательство
авторизации. Для HTTP-проверок время можно подменить через
`app.dependency_overrides[get_clock]`, без ожидания истечения 30 суток.

## Профиль и поиск

Эндпоинты профиля и поиска из таблицы требуют `Authorization: Bearer <token>`.
Исключение — скачивание аватара по подписанной ссылке, описанное ниже.

| Метод и путь | Поведение |
|---|---|
| `GET /users/me` | Свой профиль, включая `email` и `phone` |
| `PATCH /users/me` | Изменение `username` и/или `status`, ответ — свой профиль |
| `GET /users/{user_id}` | Публичный профиль без email и телефона; неизвестный ID — `404 not_found` |
| `GET /users?username=alice` | Точное совпадение username, ответ `{items: [...]}` с нулём или одним элементом |

Для username действуют те же правила, что при регистрации. Поиск чувствителен
к регистру; поиск подстроки и автоматическое обрезание пробелов не выполняются.
Статус допускает любые символы, длина — не больше 20 символов Python-строки.

В PATCH пропущенные поля не изменяются; `{"status": null}` очищает статус,
а `{"username": null}` возвращает `422 validation_error`. Пустой объект `{}`
возвращает текущий профиль. Попытка изменить другие поля, например `email` или
`password_hash`, отклоняется с `422`. Занятый username возвращает `409 username_taken`.

```bash
curl -i -X PATCH http://localhost:8000/users/me \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice_new","status":"На связи"}'
```

Внутренний `GET /internal/users?ids=<uuid>,<uuid>` выдаёт публичные профили для
сервиса чатов. Также поддерживается запись `?ids=<uuid>&ids=<uuid>`.
Список обязателен и должен содержать от 1 до 100 UUID; некорректный запрос — `422`.
Неизвестные ID пропускаются, повторы возвращаются один раз, порядок найденных
пользователей соответствует входному списку. Ответ: `{items: [...]}`.
Внутренний вызов не требует пользовательского токена и не публикуется Gateway.

При наличии аватара `avatar_url` содержит подписанный путь
`/api/v1/users/{user_id}/avatar?expires=...&sig=...`, срок действия — 15 минут
по умолчанию. У пользователей без аватара поле равно `null`.

## Аватары и S3

Перед запуском задайте `URL_SIGNING_SECRET` (одинаковый для users, chats и messages).
Например, случайное значение можно получить командой `openssl rand -hex 32`.
Храните секрет в `.env` или окружении, не в исходниках. При пустом секрете сервис
завершается с ошибкой конфигурации при старте.

Хранилище должно содержать bucket из `S3_BUCKET`. Создайте его один раз, например
из окружения сервиса при локальной SeaweedFS без проверки учётных данных:

```bash
python - <<'PY'
import boto3
from botocore import UNSIGNED
from botocore.config import Config
from app.config import Settings

settings = Settings.from_env()
client = boto3.client(
    "s3", endpoint_url=settings.s3_endpoint_url,
    config=Config(signature_version=UNSIGNED, s3={"addressing_style": "path"}),
)
try:
    client.create_bucket(Bucket=settings.s3_bucket)
finally:
    client.close()
PY
```

Bucket автоматически не создаётся. Если в хранилище настроена авторизация,
задайте вместе `S3_ACCESS_KEY` и `S3_SECRET_KEY`; используется подпись S3v4.
Если оба значения пусты, запросы к локальной SeaweedFS отправляются без подписи.
Пример выше предназначен именно для локального хранилища без авторизации.
В Compose сервису `users` передаются адреса `postgres` и `seaweedfs`, секрет и
учётные данные S3; для локального запуска адрес S3 по умолчанию — `localhost:8333`.

`PUT /users/me/avatar` принимает multipart с полем `file` и требует Bearer-токен:

```bash
curl -i -X PUT http://localhost:8000/users/me/avatar \
  -H 'Authorization: Bearer <token>' \
  -F 'file=@avatar.png'
```

Допускаются JPEG и PNG размером не более 5 × 1048576 байт. Тип определяется
Pillow по содержимому с проверкой структуры и декодирования; имени файла и
заявленному MIME-типу не доверяем. Пустой, повреждённый или другой формат —
`422 validation_error` с причиной `avatar_format`; превышение размера —
`413 file_too_large`. Успех — `200` и свой профиль с подписанным `avatar_url`.
Обработчик читает в память не больше лимита плюс один байт; multipart-парсер
может предварительно сохранять большие файлы во временный файл.

Объекты хранятся под ключами `avatars/users/{user_id}/{generated_id}`. Замена
одного пользователя сериализуется блокировкой строки PostgreSQL. Новый файл
сохраняется до обновления ссылки в БД; старый удаляется после commit.
При обычном rollback выполняется попытка удалить новый файл.
Ошибка удаления записывается в лог как `avatar_cleanup_failed`, не меняя
результат уже завершённой транзакции. PostgreSQL и S3 не образуют общей
транзакции: аварийная остановка процесса или сбой очистки могут оставить лишние
объекты; постоянная очередь повторной очистки здесь не реализована.

`GET /users/{user_id}/avatar?expires=...&sig=...` проверяет подпись и срок через
общий `UrlSigner`, затем возвращает байты с `image/jpeg` или `image/png`.
Bearer-токен не требуется. Неверная, отсутствующая или просроченная подпись —
`401 unauthorized`; отсутствующий аватар — `404 not_found`.
На границе `now == expires` ссылка уже недействительна.

Подписанный URL содержит внешний префикс `/api/v1` для Gateway. При прямом
обращении к сервису удалите этот префикс: `UrlSigner` нормализует его одинаково
при подписании и проверке. Ссылки выдаются во всех ответах с пользователями:
профиль, login, поиск, внутренний пакетный запрос. После истечения ссылки
повторно запросите профиль. В БД хранится только ключ S3, а не URL и не файл.

## Последовательность ручной проверки

При работающем локальном сервисе зарегистрируйте нового пользователя примером
из раздела регистрации. Затем получите токен (команды Bash):

```bash
users_login=$(curl --fail-with-body -sS http://localhost:8000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"alice@example.org","password":"hello123"}')
users_token=$(printf '%s' "$users_login" | python -c 'import json,sys; print(json.load(sys.stdin)["token"])')

curl -i http://localhost:8000/users/me \
  -H "Authorization: Bearer $users_token"
curl -i 'http://localhost:8000/users?username=alice' \
  -H "Authorization: Bearer $users_token"
```

Ожидается `200`; свой профиль содержит email и phone, поиск — только публичные поля.
Сохраните ID пользователя из ответа для пакетного запроса `/internal/users?ids=...`.
Для аватара используйте существующий локальный JPEG/PNG:

```bash
users_profile=$(curl --fail-with-body -sS -X PUT http://localhost:8000/users/me/avatar \
  -H "Authorization: Bearer $users_token" \
  -F 'file=@avatar.png')
users_avatar_path=$(printf '%s' "$users_profile" | python -c 'import json,sys; print(json.load(sys.stdin)["avatar_url"].removeprefix("/api/v1"))')
curl --fail-with-body -sS "http://localhost:8000$users_avatar_path" -o /tmp/kokogram-avatar-download

curl -i -X POST http://localhost:8000/auth/logout \
  -H "Authorization: Bearer $users_token"
curl -i http://localhost:8000/users/me \
  -H "Authorization: Bearer $users_token"
```

Выход возвращает `204` без тела, последующий запрос профиля — `401 unauthorized`.
Это примеры ручных запросов, автоматические тесты в рамках тикета не добавлялись.

| Что проверить | Ожидаемый результат |
|---|---|
| Регистрация с email или телефоном | `201`; в БД bcrypt-хэш с cost 10 |
| Повтор контакта с другим регистром email или записью телефона | `409 email_taken` или `409 phone_taken` |
| Повтор username при регистрации или PATCH | `409 username_taken`; остальные изменения откатываются |
| Неверный пароль или логин | `401 invalid_credentials`, новая сессия не создаётся |
| Два входа и выход из одной сессии | Вторая сессия остаётся действующей |
| Проверка токена в `/internal/sessions/verify` | `200 {user_id}`; неизвестный или просроченный — `401` |
| PATCH только одного поля / `status: null` | Остальные поля сохранены / статус очищен |
| Поиск части username | Пустой `items`, если это не полный username другого пользователя |
| Пакет из 100 / 101 ID | `200` / `422` |
| JPEG/PNG ровно 5242880 / больше 5242880 байт | `200` / `413 file_too_large` |
| Повреждённое изображение или другой формат | `422`, причина `avatar_format` |
| Замена аватара | В БД новый ключ; прежний объект удалён после commit |
| Изменённая или просроченная подпись ссылки | `401 unauthorized` |

## Связь с требованиями и границы проверки

| Требования FS | Реализация |
|---|---|
| F_Auth_1–8, F_Auth_12–14 | Регистрация, валидаторы, нормализация, уникальность PostgreSQL |
| F_Auth_9–11 | Вход по email/телефону и проверка bcrypt |
| F_Auth_15–16 | Выход из текущей сессии, несколько независимых сессий |

Архитектурные основания: HLD §1.1, §1.5, §3–3.1, §4.1–4.3, §4.6, §5.1–5.3,
§5.5. Исходные документы: [FS](../docs/FS-spec.pdf), [HLD](../docs/HLD.pdf).

На этапах реализации вручную проверялись реальные PostgreSQL и SeaweedFS,
конфликты уникальности, несколько сессий, граница срока сессии и подписанной
ссылки через `FakeClock`, приватность профилей, лимиты, rollback и одновременная
замена аватаров. Это не заменяет отдельный тикет с автоматическими тестами.
Полный E2E через Gateway и браузер, а также измерения NF_Perf_1–3 не проводились.
`/health` пока подтверждает работу процесса приложения, а не готовность БД/S3.

```bash
ruff check .

```

подтверждает готовность зависимостей. Успешный локальный Ruff не означает,
что удалённый CI уже выполнен. В PR укажите перечисленные FS/HLD, `Closes #N`
с фактическим номером тикета и результаты проверок; название PR — имя ветки.
