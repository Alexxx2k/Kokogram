# Сервис пользователей

Запуск из каталога `users` после установки `requirements.txt`:

```bash
uvicorn app.main:app --reload
```

Настройки читаются из переменных окружения. Файл `.env` автоматически не загружается:
при локальном запуске переменные нужно экспортировать в окружение процесса.

| Переменная | Значение по умолчанию / назначение |
|---|---|
| `DATABASE_URL` | URL PostgreSQL; если не задан, собирается из `POSTGRES_*` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | `kokogram` |
| `POSTGRES_HOST`, `POSTGRES_PORT` | `localhost`, `5432` |
| `S3_ENDPOINT_URL` | `http://localhost:8333` |
| `S3_REGION` | `us-east-1` |
| `S3_BUCKET` | `kokogram` |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Пустые; учётные данные выбранного S3-хранилища |
| `URL_SIGNING_SECRET` | Без значения по умолчанию; обязателен для создания `UrlSigner` |
| `SIGNED_URL_TTL_SECONDS` | `900`, допустимо от 1 до 900 секунд |
| `SESSION_TTL_DAYS` | `30`, допустимо от 1 до 30 суток |
| `AVATAR_MAX_BYTES` | `5242880`, допустимо от 1 до 5242880 байт |

`URL_SIGNING_SECRET` должен совпадать у сервисов пользователей, чатов и сообщений.
В Docker адреса зависимостей задаются именами контейнеров, например
`POSTGRES_HOST=postgres` и `S3_ENDPOINT_URL=http://seaweedfs:8333`.

Настройки и общие зависимости предоставляются функциями в `app/api/dependencies.py`.
В HTTP-проверках их можно подменять через `app.dependency_overrides`.
Обработчики ошибок и JSON-логирование подключены в `app/main.py`; middleware
сохраняет входящий `X-Request-ID` или создаёт новый и возвращает его в ответе.

На этом этапе `/health` возвращает `{"status": "ok"}` и подтверждает работу приложения;
проверки доступности PostgreSQL и S3 ещё не подключены.

## Слой данных

`app/models.py` содержит обычные Python-объекты `User` и `Session`. Интерфейсы
репозиториев находятся в `app/ports/`, реализации SQLAlchemy — в `app/adapters/`.
Адаптеры используют асинхронный psycopg 3; версии SQLAlchemy и psycopg совпадают
с зависимостями миграций.

Пул подключений создаётся при запуске приложения и освобождается при остановке.
DI-функции `get_user_repository` и `get_session_repository` используют общую
сессию БД в рамках запроса. Транзакция завершается до отправки ответа: при успехе
выполняется commit, при исключении — rollback. Репозитории сами не делают commit.

Описания таблиц соответствуют миграции `0001_users`; автоматически таблицы не
создаются. Перед обращением к БД необходимо применить миграции из корня проекта.
ID и временные поля обязательны при создании объектов: их передаёт бизнес-логика
через `IdGenerator` и `Clock`. У репозиториев нет генераторов ID и времени.

Конфликты ограничений `uq_users_email`, `uq_users_phone` и `uq_users_username`
преобразуются в `email_taken`, `phone_taken` и `username_taken` соответственно.
Ошибки подключения и таймауты преобразуются в `service_unavailable`.
Другие нарушения целостности не маскируются под конфликты пользователя.

Репозиторий сессий принимает только `token_hash`; вычисление SHA-256 и проверку
`expires_at` выполняет `SessionService`.

## Регистрация

`POST /auth/register` принимает JSON с `username`, `password` и хотя бы одним
из полей `email` и `phone`. Авторизация не требуется. Пример для локального
сервиса (при запуске через Gateway добавляется префикс `/api/v1`):

```bash
curl -i http://localhost:8000/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"hello123","email":"Alice@Example.org"}'
```

Правила:

- Username: от 3 до 12 символов, латинские буквы, цифры и `_`.
- Пароль: от 6 до 12 символов, хотя бы одна буква и одна десятичная цифра.
  Пароль не обрезается и не нормализуется; буквы могут быть нелатинскими.
- Email проверяется библиотекой `email-validator` без DNS-запросов и сохраняется
  в нижнем регистре; пробелы по краям удаляются.
- Телефон: 11 цифр с началом `8` или `7`, либо международная запись с `+7`.
  Пробелы, круглые скобки и дефисы допускаются. Результат — `+7XXXXXXXXXX`.
- Если переданы и email, и телефон, проверяются и сохраняются оба.

При успехе возвращается `201` и объект `{id, username, status, avatar_url}`.
У нового пользователя статус и аватар равны `null`. Email, телефон и хэш пароля
в этот ответ не включаются. Регистрация не создаёт сессию входа.

Нарушения правил возвращают `422 validation_error` с полем и причиной
в `error.details`; конфликты уникальности — `409 email_taken`, `phone_taken`
или `username_taken`. Пароль хэшируется bcrypt с cost 10 в отдельном потоке,
в БД передаётся только хэш. Нагрузочные требования NF_Perf_1–3 пока не измерялись.

## Вход и сессии

`POST /auth/login` принимает JSON `{login, password}`. Логин — email или российский
номер телефона; используются те же правила нормализации, что при регистрации.
При неверном логине или пароле возвращается `401 invalid_credentials`.

```bash
curl -i http://localhost:8000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"Alice@Example.org","password":"hello123"}'
```

Успешный ответ: `200`, `{token, expires_at, user}`. `user` содержит те же поля,
что ответ регистрации. Токен создаётся `TokenGenerator` (в обычном запуске —
32 случайных байта в URL-safe представлении). Исходный токен возвращается клиенту;
в PostgreSQL сохраняется только его SHA-256 хэш. Время создания берётся из `Clock`,
срок действия — `SESSION_TTL_DAYS` (по умолчанию 30 суток). Каждый вход создаёт
отдельную сессию, предыдущие сессии продолжают действовать.

`POST /auth/logout` требует `Authorization: Bearer <token>` и удаляет только текущую
сессию. Успех — `204` без тела; отсутствующий, неизвестный или просроченный токен —
`401 unauthorized`. Остальные сессии пользователя не удаляются.

Внутренний `POST /internal/sessions/verify` принимает JSON `{token}` и возвращает
`200`, `{user_id}`. Токен ищется по хэшу; при `clock.now() >= expires_at` он уже
недействителен. Пустой, неизвестный, просроченный или завершённый токен возвращает
`401 unauthorized`. Этот эндпоинт предназначен для Gateway; наружу пути `/internal`
не маршрутизируются. Проверка срока не продлевает сессию.

Просроченные записи сейчас остаются в таблице, но не принимаются при авторизации;
фоновая очистка не реализована.

DI-функция `get_current_user` проверяет Bearer-токен через `SessionService` и
получает пользователя из репозитория. Она используется защищёнными эндпоинтами
профиля; заголовок `X-User-Id` не используется как самостоятельное доказательство
авторизации. Для HTTP-проверок время можно подменить через
`app.dependency_overrides[get_clock]`, без ожидания истечения 30 суток.

## Профиль и поиск

Все внешние эндпоинты `/users` требуют `Authorization: Bearer <token>`:

| Метод и путь | Поведение |
|---|---|
| `GET /users/me` | Свой профиль, включая `email` и `phone` |
| `PATCH /users/me` | Изменение `username` и/или `status`, ответ — свой профиль |
| `GET /users/{user_id}` | Публичный профиль без email и телефона; неизвестный ID — `404 not_found` |
| `GET /users?username=alice` | Точное совпадение username, ответ `{items: [...]}` с нулём или одним элементом |

Для username действуют те же правила, что при регистрации. Поиск чувствителен
к регистру; поиск подстроки и автоматическое обрезание пробелов не выполняются.
Статус допускает любые символы, длина — не больше 20 символов Python-строки.

В PATCH пропущенные поля не изменяются; `{"status": null}` очищает статус,
а `{"username": null}` возвращает `422 validation_error`. Пустой объект `{}`
возвращает текущий профиль. Попытка изменить другие поля, например `email` или
`password_hash`, отклоняется с `422`. Занятый username возвращает `409 username_taken`.

```bash
curl -i -X PATCH http://localhost:8000/users/me \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice_new","status":"На связи"}'
```

Внутренний `GET /internal/users?ids=<uuid>,<uuid>` выдаёт публичные профили для
сервиса чатов. Также поддерживается запись `?ids=<uuid>&ids=<uuid>`.
Список обязателен и должен содержать от 1 до 100 UUID; некорректный запрос — `422`.
Неизвестные ID пропускаются, повторы возвращаются один раз, порядок найденных
пользователей соответствует входному списку. Ответ: `{items: [...]}`.
Внутренний вызов не требует пользовательского токена и не публикуется Gateway.

Ссылки на аватары пока возвращаются как `null`: загрузка и выдача подписанных
ссылок будут подключены отдельным этапом.
